# Trust discipline — why okfhub renders dated evidence, never verdicts

This is the single most important concept in this bundle. If you read only one,
read this one.

## The rule

**okfhub never issues a verdict.** There is no "approved" badge, no "trusted"
label, no "verified-safe" stamp, no green checkmark, no composite score. What
okfhub provides instead is **dated, factual evidence** — rows of who/what/when
— and lets the consumer reason about it.

## Why: the May-2026 npm Sigstore compromise

In May 2026, the npm ecosystem suffered a Sigstore-signing compromise: packages
that had been cryptographically "signed" and carried trust signals were
nevertheless used to deliver malicious payloads, because the *signal* (signed)
had come to be read as a *verdict* (safe). The signing was real; the inference
"therefore safe" was the failure.

okfhub's discipline is the direct lesson. A signal like "this is a
GitHub-verified organization" is a **fact about provenance**. It is useful
context. The moment it is rendered as "therefore safe to run", the registry has
taken on a liability it cannot discharge — it has implicitly promised the
absence of malice, which no registry can promise for arbitrary content.

So okfhub renders the fact ("GitHub-verified organization · last verified
<date>") and stops there. The consumer decides.

## Two axes, never merged

okfhub surfaces trust on **two distinct axes**, and they are deliberately never
collapsed into one score:

1. **Publisher trust** (registry-computed) — facts about the *source*. The
   structural checks (frontmatter parses, type present, links resolve), the
   verified-org signal, the host-popularity numbers, the DNS-verified-domain
   for HTTP-served bundles. The registry vouches for the *source*.
2. **Content trust** (author-asserted, OKF v0.2) — facts about the *content*.
   The `generated`/`verified` frontmatter families. The *author* vouches for
   the *content*.

See [[evidence-reading]] for how to read each axis, and
[[reputation-signals]] for the publisher-signal vocabulary. The key point here:
**these two axes co-exist as separate, clearly-labeled rows, never one badge.**

## What this means for THIS bundle

This bundle is first-party — the okfhub team authored it. It adopts v0.2
frontmatter (`generated: { by: human:okfhub-team }`, `verified` entries — see
the frontmatter above). That frontmatter is rendered exactly as it would be
for any third-party bundle: a dated-evidence row saying "generated by
human:okfhub-team" or "verified by human:okfhub-team". It is **not** rendered
as a green "approved" badge, because there is no such badge. okfhub vouching
for its own content is a claim *you* evaluate — it is data, not a verdict.

This is why the [[vocabulary-invariant]] exists: the forbidden words
(approved/trusted/verified-safe/popular/trending/best) exist precisely to
prevent the registry from accidentally issuing a verdict in its own copy.

## The procedural-vs-declarative boundary (again)

Trust discipline is also why this bundle is *reference material*, not
*instructions*. A bundle that taught procedures and was treated as trusted
guidance would create exactly the verdict-it-is-safe-to-execute failure mode
the npm compromise demonstrated. The skills are the procedural authority; this
bundle is context. See [[index]] and [[mcp-vs-local-install]].
